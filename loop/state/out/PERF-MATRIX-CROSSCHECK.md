# 交叉核查 `perf:baseline-matrix`（另一个 agent 的性能矩阵）

**日期**：2026-10-08 · 我**没有**跑 GPU（`maxGpuLeases=1`，该租约由 `w-gpu` 持有）
**方法**：读它的 artifact + raw 证据，与我 00:12 的独立测量对照

---

## 一、先说**它对的地方**（不抹掉）

| 项 | 它的做法 | 评价 |
|---|---|---|
| 驱动 | `--headless=new --use-angle=metal`（`CL_GPU=1`）**真 GPU** | ✅ 不是 SwiftShader |
| 帧时口径 | rAF 帧间隔（真实墙钟 `performance.now()`），**非 pump / 非 fixedDt** | ✅ 与我们既有教训一致 |
| 分位数 | **合并后的原始帧间隔**重算，长窗 ≤25s 分段、段间不暂停 | ✅ 正确 |
| 长任务 | `PerformanceObserver('longtask')` 与帧间隔**分开**记 | ✅ |
| 渲染计数 | `renderer.info` 关 `autoReset`、在**一帧边界**累积整个 composer | ✅ 这点比多数人细致 |
| 档位钉死 | 每阶段（**含每个长时窗口**）重新钉档并**回读校验**，不符即标 `tierMismatch` 不参与结论 | ✅ 很强 |
| 不声称 | 明写「不声称稳定 60fps」「不把短窗口当长时」「不把降档冒充原生 4K」 | ✅ 诚实 |

**⇒ 这份工作的**方法学是合格的**，我不质疑它的手法。**

## 二、但有三处**与计划门限不符**，且都在它自己的数据里

### ① 路径叫 `steady-2min`，实际只测了 **20 秒**

```
dafeng: measuredSeconds=20.02   fps=35.972
xiangyou: measuredSeconds=20.01  fps=39.087
sanguo: measuredSeconds=20.02   fps=37.156
```

**计划 §04 明文**：「桌面稳态 | 60Hz目标机均值≥59fps，P95≤18ms… | **每图每书连续2分钟**，不混合最慢作品」。

**⇒ 20.02 秒 ≠ 2 分钟。** 而这条门限**正是**我在早先轮次踩过的坑：
我的 8 秒短测得 **52.2fps**，2 分钟稳态得 **48.5fps** —— **短测系统性偏乐观**。
**⇒ 这份矩阵的稳态数字**不能作为 2 分钟稳态的证据**。

### ② 用**旧图**测：「旧缓存兼容样本」被当成「当前交付样本」

```
它测的: data/cache/9b676d7031b1bcd3b8377a18.json   10,349,343 字节   事件 2,990
生产在: f6a657935c945a3a9bcfc000                    64,024,751 字节   事件 17,705
```

**`9b676d7031b1bcd3b8377a18` 正是计划 §02 #7 点名的那份**
（「旧2990事件、旧缓存的4K与小屏结果**不能覆盖当前17705事件、63MB大奉**」）。
**⇒ 它就是"2990 事件"那个被警告过的样本。**

**但这里有个反转**：它的**渲染负载其实相近** ——
三版图的**人物数完全相同（453）、关系数相同（2106）、营地相同（10）**，
而事件数从 2990 → 17705 差 6 倍。
**⇒ 事件数对星座视图的渲染负载几乎无影响**（事件不直接进星座几何）。

**⇒ 所以这一条**不是「用小数据冒充大数据」**，而是**「测的不是计划指定的当前交付版本」**。
**两者都要说清，我不把它夸大成"造假"。**

### ③ `steady` 的 **35.97fps 与我 00:12 的 48.48fps 差 35%，而源码 hash 完全相同**

```
它记录的源码: scene-core.js 92d82dc7…  app.js 3342e65e…  index.html 079547a3…
我现在的源码: scene-core.js 92d82dc7…  app.js 3342e65e…  index.html 079547a3…   ← 逐位相同
```

**⇒ 同一份代码、同一档位（`dpr=1 / maxPixels=8300000 / boost=1 / boostPin=1 / samples=2 / degrade=0`）、
同一个视图（`context=constellation`），帧率差 35%。**

**⇒ 这是一条**独立性能结论**：当前的 4K 稳态测量**不可复现**。**
- 可能原因：并发负载（我的测量在 00:12，它在 03:28；期间有别的 GPU/CPU 活动）、
  或者两次的暖机/静置时长不同、或机器热状态不同。
- **无论哪种原因，结果都是：单次 4K 稳态数字不能作为验收证据。**

## 三、我的结论

| 项 | 结论 |
|---|---|
| 方法学 | ✅ 合格（真 GPU、真实帧时、分位数重算、档位回读校验） |
| **稳态时长** | ❌ **20s ≠ 计划要求的 2 分钟** ⇒ 数字不能直接当门限证据 |
| **测量版本** | ⚠️ 用旧图（2990 事件）；**但渲染负载与当前版本相近**（人物/关系相同）⇒ 是"版本不符"而非"负载不符" |
| **可复现性** | ❌ **同代码同档位差 35%** ⇒ 4K 稳态结论**不可复现**，这才是最要紧的问题 |

**⇒ 我不改它的产物（它是别人的工作）；我把这份交叉核查作为复核意见留档。**
**⇒ 最重要的建议是：4K 稳态门限必须以**2 分钟**、**在显式记录机器热状态与并发负载**的条件下重测，
且**至少两次**以证明可复现。**

## 四、沉淀规则（第 27 条）

> **同一份代码、同一档位、同一个视图，两次测量差 35% —— 这个差值本身就是结论。**
> 我原本想"用我的数字纠正它的数字"，但两个数字**都不能**作为门限证据：
> **一个测了 20 秒（不是 2 分钟），另一个测了但复现不了。**
> **⇒ 性能门限的证据标准必须包含"可复现"这一项**，
> 否则单次漂亮数字与单次难看数字同样无意义。

# 五、补充核查：把「可复现性」用**我自己的重复测量**量化

我不跑 GPU（租约在 `w-gpu` 手里），但**我已有的多次 2 分钟稳态**正好能回答这个问题。

## 我的 4 次 2 分钟原生 4K 稳态（同档位：`dpr=1 / boost=1 / boostPin=1 / samples=2 / degrade=0`）

| 目录 | 数据 | fps | p50 | p95 | >33.4ms | 时长 |
|---|---|---:|---:|---:|---:|---:|
| `steady-dafeng-2x` | 54.9MB | **52.18** | 19.1 | 21.5 | **0** | 145.1s |
| `steady-xiyou` | — | 51.52 | 19.3 | 21.7 | 0 | 145.0s |
| `steady-dafeng` | 54.9MB | **48.48** | 20.5 | 23.1 | 0 | 145.0s |
| `steady-sanguo` | — | 47.30 | 21.0 | 23.9 | 0 | 145.1s |

**⇒ 中位 50.00 · 极差 4.88（9.8%）。**

## 关键：**同书、同数据、同代码、同档位**的两次（相隔 9 分钟）

```
steady-dafeng      48.48fps   报告 mtime 10-08 00:12:39   data=9f9c852f…  coreSha=92d82dc7…
steady-dafeng-2x   52.18fps   报告 mtime 10-08 00:21:57   data=9f9c852f…  coreSha=92d82dc7…
```

**⇒ 同条件复现差 7.6%。**

## 段内稳定、段间不稳（这是最有信息量的一条）

每 25 秒一段的读数：

```
steady-dafeng-2x   52.3 51.1 52.4 52.4 52.5      ← 段内极差 1.4
steady-dafeng      48.5 48.3 48.0 48.7 48.9      ← 段内极差 0.9
steady-sanguo      47.5 47.9 47.6 47.0 45.9
steady-xiyou       51.7 51.7 52.2 51.4 50.3
```

**⇒ 每一次运行**内部**非常稳定（±1fps），但**不同次运行之间**差 3.7fps。**

**这排除了「帧率抖动大、需要更长窗口」的解释** ——
问题是**运行级的系统性偏移**（热状态、后台负载、GPU 时钟状态…）。

## 与他们的数字合并

| 来源 | 窗口 | fps |
|---|---:|---:|
| 他们 `steady-2min/dafeng` | **20.0s** | **35.97** |
| 我 `steady-dafeng` | 145.0s | 48.48 |
| 我 `steady-dafeng-2x` | 145.1s | 52.18 |

**⇒ 合并区间 35.97 – 52.18 fps（跨实现差 35%）。**

**⚠ 我自己的一次撤回**：我先前试图把我的 145 秒**切成前 20 秒**来对比，
得到「前 20 秒 48.36fps」——**但那个计算是错的**：
`sample['_deltas']` 只存了**一个 25 秒段**（1213 条），不是整段 7031 帧。
**⇒ 我撤回了那个分段结论**，改用 `_segments`（每 25 秒一段，5 段）。
**这正是"先核实字段语义、再计算"的又一次应用。**

## 结论（不改他的产物，只留复核意见）

1. **他的方法学合格**；
2. **20s ≠ 计划要求的 2 分钟** ⇒ 不能直接当门限证据；
3. **用旧图（2990 事件）**，但**渲染负载与当前版本相近**（人物/关系/营地完全相同）⇒ 是版本不符而非负载不符；
4. **最要紧**：同代码同档位的 4K 稳态**跨运行差 7.6%（我的两次）、跨实现差 35%（我 vs 他）**
   ⇒ **单次数字不能签收；门限证据必须包含"可复现"这一项，且需 ≥2 次同条件复现。**
