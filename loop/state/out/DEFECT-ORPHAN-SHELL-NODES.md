# 缺陷：星盘上有 **44 个空壳人物节点**（0 事件、0 关系），其中 2 个是他人名字的截断

**版本**：`aee4c99808674e4220ab0104`（大奉 17705 事件 / 453 人物 / 2106 关系）
**方法**：只读数据 + 源码路径核对（**不跑 GPU**）

---

## 一、缺陷与用户损失

**现象**：角色表里有 44 个条目**既不被任何事件引用、也不被任何关系引用**
（`events[].characters` 无它，`relations[].a/b` 也无它）。

**用户损失**：星盘按 `name` 建索引（`app.js:562`），
**这 44 个条目会各自成为一颗"没有任何内容的星"** ——
用户点开它看不到剧情点和关系，只看到一个名字。

**其中 2 个更严重：它们是别的角色的名字截断**

| 空壳 | 原文频次 | 完整角色 | 该完整角色的事件/关系 |
|---|---:|---|---|
| **`李慕`** | 207 | `李慕白` | **119 事件 / 23 关系** |
| **`文宣`** | 160 | `葛文宣` | **91 事件 / 14 关系** |

**⇒ 用户会在星盘上同时看到 `李慕` 和 `李慕白` 两颗星，
而 `李慕` 是空的、`李慕白` 才有内容。**

## 二、实测证据（可复现）

```
关系以『李慕』为端点:   0 条       关系以『李慕白』为端点: 23 条
事件引用『李慕』:       0 条       事件引用『李慕白』:   119 条
```

**⇒ `李慕` 是一个**完全孤立的空壳**：0 事件、0 关系连到它。
它的全部 23 条关系里的端点写的都是 `李慕白`（全名），
所以那 23 条关系**属于 `李慕白`**，与 `李慕` 无关。**

**⇒ 这不是"关系被算两次"，而是"多了一个没人用的条目"。**

## 四、判定：哪些该删、哪些该并

| 类别 | 判据 | 处置 |
|---|---|---|
| **A. 他人名字的截断** | 存在另一角色的名字**以它开头**，且**原文频次更高、有事件** | **合并**（`李慕`→`李慕白`、`文宣`→`葛文宣`）：把短名加入长名的别名，删掉空壳条目 |
| **B. 原文确有但无事件** | 原文出现 ≥1 次，且**不是**他人名字的前缀 | **保留**（它确实是原著里的人物/称呼，只是本图未抽到它的剧情点）—— 但应标为无内容的孤立点，**不应与主角同权重显示** |
| **C. 原文 0 次** | 原文找不到 | **可疑**（可能是抽取幻觉），需逐个核 |

**⇒ A 类只有 2 个（李慕、文宣），B/C 类占其余 42 个。**

## 五、为什么我**不**直接删这 44 条（边界说明）

1. **A 类的"合并"要动角色表**（删除条目 / 加别名），
   而 `characterAliasFixes` 只能**移除**别名、不能添加 —— **需要新通道**；
2. **B 类不能删**：它们是原文真实存在的人物，
   只是**本图没有抽到它们的剧情点** —— 删掉等于**隐藏"这里有个我没抽到的人物"这一事实**；
   正确做法是**在生产侧标为"无内容孤立点"**并降低显示权重（`tierOf` 已把它算作 tier 4，
   **但那 44 个里有些因 `role='功能性'` + 关系数 0 ⇒ tier 4 ⇒ **已经会被折叠**，
   所以**界面影响有限**）；
3. **C 类必须先读原文**才能定，不能机械删。

**⇒ 结论：A 类（2 个）值得修且有明确依据；B/C 类需要生产侧与人工判断，我不擅自删。**

## 六、`李慕`/`文宣` 是否真的会被用户看到？

我核对了 `tierOf`（`app.js:1794`）：
```
role='功能性' + importance=10 + 事件 0 + 关系 0  ⇒ **tier 4**
```
而 `app.js:1784` 的文案是「零剧情点、无关系的功能性角色共 N 位：
**折叠时只作为群像层微点存在，不占标签预算**」。

**⇒ 产品**已经**把它们折叠为群像层微点，**不占标签预算**。
**⇒ 用户损失是"群像层多 2 个微点"，而不是"星盘上多两个显眼的大星"。**

**⇒ 我把严重性如实下调**：这是一个**真实的、但影响有限**的缺陷。

## 七、沉淀规则（第 35 条）

> **发现缺陷后，下一步不是"能修就修"，而是"量化它的用户可见后果"。**
> 我一开始准备把 44 个空壳当成严重问题（"星盘上有 44 颗空星"）。
> 读了 `tierOf` 与 `app.js:1784` 的文案后，**真实后果是"群像层多几个微点"** ——
> 因为产品**本来就把"零剧情点、无关系"的角色折叠掉了**。
> **⇒ 一个在数据层明显的异常，可能在产品层已被正确地降权处理；
> 不核产品路径就报缺陷，会高估严重性。**

# 八、深一层：那 12 个"原文 0 次"的空壳**不是幻觉，是诚实的占位条目**

我把 44 个空壳按原文频次细分：

| 类 | 原文次数 | 个数 |
|---|---|---:|
| B | ≥1 次 | 32 |
| **C** | **0 次** | **12** |

**C 类 12 个**：`九尾天狐遗孤`、`国子监祭酒`、`太平刀器灵`、`度厄使团僧人`、
`戚广伯等云州核心`、`戚广伯麾下将领赵秉`、`昏聩族老`、`柴杏儿等红颜知己`、
`白鹤观观主`、`许七安的丫鬟`、`许七安的丫鬟2`、`许平峰之妻以外的家人`。

**看起来最像"AI 编造"的两个**：

```
'许七安的丫鬟'
   brief = '玲月身边的丫鬟，在井边受到惊吓。**材料未提供其姓名、言行与任何剧情细节**，
            仅有身份与受惊一事，人物面貌不…'

'许七安的丫鬟2'
   brief = '**材料仅显示其为临安公主府宫女**、以丫鬟身份出现在许七安身边，属功能性配角。
            **没有任何言行、抉择与剧情记录**'
```

**⇒ 这两个条目的 `brief` **自己就写明了**「材料未提供其姓名」「没有任何言行与剧情记录」。**

**⇒ 它们**不是**幻觉：系统知道原文里没有这个名字，
于是**用"许七安的丫鬟"这样的描述性占位名**把它登记下来，**并在 brief 里声明信息缺失**。

**⇒ 这与本仓的 READER 契约一致**：
> 用未知填默认值 | 缺字段写 null，不要写 0 / 0.5 / 「未提及」以外的编造值

**⇒ 系统在这一点上是**诚实**的：它没有编一个丫鬟的名字，而是把"这里有个我认不出的人"如实登记。**

## 九、那么真正的问题是什么

不是"编造"，而是**命名口径与显示口径**：

| 问题 | 性质 |
|---|---|
| `许七安的丫鬟` / `许七安的丫鬟2` 这类**描述性占位**混在 `characters` 里 | 数据卫生：它们**不是名字**，是"某人的丫鬟"这一角色槽位 |
| `李慕` / `文宣` 这类**截断** | **真缺陷**（合并即可） |
| 12 个原文 0 次的条目 | 需区分「诚实占位」（如上）与「抽取噪声」 |

**⇒ 我修的是 A 类（2 个截断）；其余 42 个我**不删**，因为：**
- 删掉 B 类等于**隐藏"这里有个我没抽到的人物"**；
- 删掉 C 类里的诚实占位，等于**把系统的诚实标记当成噪声清掉**。

## 十、沉淀规则（第 36 条）

> **"原文里找不到"的条目，可能是**幻觉**，也可能是**诚实的占位**——
> 判据是看它**自己有没有声明信息缺失**。**
> 我看到 `许七安的丫鬟2` 时的第一反应是"这是 AI 编的"。
> 读了 `brief` 才发现：**它写着「材料未提供其姓名」「没有任何言行、抉择与剧情记录」。**
> **⇒ 一个条目"原文找不到"不等于"它在撒谎"；
> 它可能正在**如实记录"我知道这里有人，但我不知道是谁"** —— 而那是**正确**的行为。**
