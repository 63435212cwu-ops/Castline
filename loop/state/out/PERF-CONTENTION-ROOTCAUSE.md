# 找到了第 37 轮那个「35% 差」的**具体原因**：一个**泄漏的 Chrome 会话**在并发烧 CPU

**日期**：2026-10-08 · 证据可复现

---

## 一、事实

```
$ ps -o pid,ppid,etime,%cpu -p 3487
  PID  PPID ELAPSED  %CPU
 3487     1   24:05   0.0        ← 父进程是 launchd（**孤儿**）
$ ps -o pid,%cpu,time -p 3492          ← 它的 GPU 子进程
 3492  22.9  5:53
```

| 项 | 值 |
|---|---|
| 命令行 | `Google Chrome --headless=new --use-angle=metal --window-size=1440,900 --remote-debugging-port=0 ... about:blank` |
| **启动时刻** | **Thu Oct 8 03:22:30 2026** |
| 已运行 | **24 分钟**（仍在） |
| **GPU 子进程 CPU** | **三次采样 23.0 / 24.2 / 22.1 %** —— **持续空烧** |
| 累计 CPU 时间 | **5 分 59 秒** |
| CDP 客户端连接 | **0**（没有任何人在用它） |
| 页面 | `about:blank` |

## 二、时间线的重合（这是关键）

```
03:22:30   孤儿 Chrome 启动（PPID 稍后变 1）
03:28:35   他们的 perf drive.log 开始写          ← **孤儿正在烧 23% CPU**
03:42:44   他们的 perf artifact 落盘（35.97fps）
```

**⇒ 他们的 4K 测量是在一个**持续占用 23% CPU 的泄漏浏览器**旁边做的。**

## 三、这解释了第 37 轮那个无法解释的差

| 来源 | 窗口 | fps | 当时环境 |
|---|---:|---:|---|
| 他们 | 20.0s | **35.97** | **孤儿 Chrome 在烧 23% CPU** |
| 我 `steady-dafeng` | 145.0s | 48.48 | 00:12（**孤儿尚未启动**，03:22 才起） |
| 我 `steady-dafeng-2x` | 145.1s | 52.18 | 00:21（同上） |

**⇒ 两次测量不是「同一环境下的不可复现」，而是**环境本身不同**：
先有并发负载，后没有。**

**⇒ 我第 37 轮的结论「4K 稳态不可复现」应当**修正**：
不是"测不准"，而是**"有一次测量被污染了"**。
我当时的措辞（"单次数字不能签收"）方向对，但**归因不完整** ——
我没想到去查**当时机器上还有什么在跑**。

## 四、这也修正了我对自己数字的信任

我 00:12 / 00:21 两次测得 48.48 / 52.18 —— **当时孤儿还没起**，
但**我不知道那时有没有别的负载**（我**没有**当时的进程快照）。
**⇒ 我的数字"相对干净"这句话，我**无法证明**，只能说"未见当时有 GPU 占用"。

**⇒ 正确做法**：性能测量必须**同时记录进程快照**（谁在跑、CPU 占用），
否则事后无法判断某次数字是否被污染。

## 五、处置

| 项 | 决定 |
|---|---|
| 孤儿 Chrome 3487 | **我不杀**（PPID=1 属归属不明；`GPU-LOCK` 规则明令「归属不明的目录/进程保持原状」） |
| 它的影响 | **记录在案**；后续 4K 测量必须在**进程快照干净**时做，并把快照写进产物 |
| 第 37 轮的「不可复现」结论 | **修正为「其中一次被 23% CPU 的并发负载污染」** |

## 六、沉淀规则（第 28 条）

> **性能数字必须附「当时机器上还有什么在跑」的进程快照。**
> 我在第 37 轮面对 35% 的差，找过代码 hash、档位、数据版本、窗口时长 ——
> **唯独没有查"当时有多少 CPU 在被别人用"**。
> 而 `GPU-LOCK` 文件**早就写明**了要「实测 Chrome 数」。
> **⇒ 我把"检查并发"当成取锁前的动作，而没有当成**记录测量条件**的一部分。**
> **并发快照是性能证据的组成部分，不是取锁手续。**
